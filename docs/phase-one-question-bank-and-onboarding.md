# Phase 1 question bank and onboarding plan

For the authoritative curriculum identity and tagging contract, see [Curriculum and question tagging](curriculum-and-question-tagging.md). The [import plan](question-import-and-filtering-plan.md) covers provenance and publication.

## Baseline and constraints

The existing site is a static, browser-local application. Its guest flow keeps progress in memory and can transfer it to a new local account; existing accounts must remain readable. The current catalogue has 38 subjects, 926 paper records including 40 demo papers, and 249 sample questions. Catalogue entries are not question extracts. The practice engine already supports specification ranges, part identities, dependencies and several filters; reuse those models. The authored specification tree order is a provisional fallback unless an independently verified `point_order` is supplied. No verified year or textbook mappings were found in the repository. Do not invent mappings, question content, permissions or examiner reports.

## Batches

1. **Onboarding and navigation:** remove public demo-account entry points while retaining labelled demo questions. Keep subject, board, colour and target controls. Make coverage selection a draft within onboarding, with save, cancel, add-another and finish paths. Isolate subject selections and maintain keyboard and mobile usability. Clarify subject-page metrics and make individual questions the primary action, with papers secondary.
2. **Curriculum representation:** keep specification codes as strings and stable IDs. Model source-verified year and textbook edition/chapter mappings separately from official trees, including many-to-many and partial coverage. Only expose verified mapping choices; document missing sources and avoid automatic learned-state changes when viewing a year. Preserve existing tree ordering as provisional when no verified syllabus order exists.
3. **Question discovery and filtering:** default to individual questions and retain existing deep links and explicit test building. Separate search selection from saved learned coverage. Implement strict selection as a primary intersection plus all genuinely required points within the selected leaves; crossover mode may broaden this and must show additional requirements. Compose distinct groups with AND, choices within a group with OR, and explain exceptions. Keep stale saved filters visible and removable. Default to newest using paper metadata; retain original part order within a paper. Shuffle the full matching set with a stable seed before pagination and reshuffle only on request.
4. **Cards, marks and progress:** render selected assessable parts with shared context and optional full-question context, schemes and accurate sources. Mark only on a deliberate save, distinguish unmarked, zero, partial and full, and preserve prior attempts and canonical IDs. Editing must not create accidental duplicates; a deliberate reattempt is distinct. Guest account handoff must retain the current search and work. Provide useful latest-attempt progress filters and avoid conflicting states.
5. **Sets and sources:** keep a canonical deduplicated selection across searches, with count, total, review and explicit start. Avoid parent/child double-counting. Only expose verified available sources and report links; label paper-level material and missing content honestly. Do not scrape or import third-party questions.
6. **Documentation and verification:** update the import plan with provenance, permissions, stable revisions, part dependencies, source regions, mapping and review requirements, and a difficulty rubric. Separate implemented functionality, verified evidence, provisional data and future ingestion. Run existing and focused regression tests. Exercise guest and existing-account paths, two-subject onboarding, strict ranges, inline marking, reload, shuffle, sets and context in a browser; check desktop, tablet, phone, keyboard access and overflow. Report any data or access blockers precisely rather than fabricating a mapping or source.

## Data safety and delivery

Keep browser accounts, attempts and content identifiers compatible. Any new storage field must tolerate missing historical data; add migrations only where needed and test old records. Avoid claims of cross-device sync. Preserve homepage free-access copy and notebook styling. Source and textbook verification are independent of UI work and must not block safe improvements elsewhere.
